# Appendix D — Architecture Decision Record Index

Each decision is documented on a single page recording context, options considered, the decision taken and its consequences. The full records are maintained in [`docs/architecture/decision-records.md`](../architecture/decision-records.md).

| ADR | Decision | Principal alternatives considered |
|---|---|---|
| ADR-001 | Layered architecture with a single authoritative ASP.NET Core API as the only public backend. | Direct client-to-database access; a backend-for-frontend per client; microservices per component. |
| ADR-002 | Delegate authentication and user directory to ThunderID; retain authorisation in the API. | ASP.NET Core Identity with local credential storage; a custom JWT issuer; a different hosted identity provider. |
| ADR-003 | React state management: feature-scoped custom hooks for server state, ThunderID SDK context for session state (revised 2026-10-04; TanStack Query + Zustand was the original proposal and was not adopted). | TanStack Query + Zustand; Redux Toolkit throughout; Context API only. |
| ADR-004 | Flutter state management: Riverpod. | BLoC; Provider; setState with a service locator. |
| ADR-005 | LangGraph as the agentic framework and orchestration method. **Superseded by ADR-010 (2026-09-15)** — its graph primitives (typed state, checkpointed persistence, conditional edges, human-approval interrupt) proved implementable directly in C#, so the Python/LangGraph runtime is no longer part of the target architecture; see §7.2.1. | Microsoft Agent Framework; a custom orchestrator in C#; a linear prompt chain. |
| ADR-006 | Attribute-value tables for custom asset attributes; JSONB for agent workflow state. | JSONB for both; typed columns per domain; a document database alongside PostgreSQL. |
| ADR-007 | Superseded by ADR-011. | — |
| ADR-008 | IBM Carbon Design System as the React client's component library and visual language. | A custom component library; Material UI; Tailwind CSS with hand-built components; Ant Design. |
| ADR-009 | Cloudflare R2 (S3-compatible) as the default photographic-evidence object store for CoreGrid-operated editions, behind an `IFileStorageService` abstraction (Section 11.3). | AWS S3; Azure Blob Storage; storing the object in PostgreSQL as a `bytea` column; mandating a single fixed provider with no self-hosted alternative. |
| ADR-010 | Consolidate the agentic subsystem into the single ASP.NET Core API deployable: one in-process orchestrator (`AgentWorkflowService`) plus four agent services; model access only through configurable OpenAI-compatible endpoints (`LlmSettings`), used by the Planner and Budget Analysis nodes with deterministic fallbacks (§7.2.1). Motivated by CoreGrid's M0 one-deployment-per-customer model (§4.1, §19.10) — fewer independently-deployed runtimes means a smaller security-review surface and lower operating burden for a self-hosted enterprise product — and by cost: every node that doesn't need a model call is one fewer inference charge per workflow run. See §7.2.1, §3.6. | Keep the per-node split from ADR-005 (Python/LangGraph for Planner and Budget Analysis, .NET-native for the other two) as a permanent hybrid; adopt Mastra (Node.js) as a third framework/runtime; one centralised Python/LangGraph service hosting every model-calling node instead of per-node Python services. |
| ADR-011 | Container-friendly, platform-neutral, self-hosted deployment: separately deployable API and web images, environment-variable configuration, `/health` and `/swagger`, migrations applied before start-up. | One fixed cloud PaaS; local-only setup; a single combined process. |
