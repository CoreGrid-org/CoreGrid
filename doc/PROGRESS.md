The agentic subsystem's target architecture, locked in 2026-09-15 ([SRS §7.2.1](SRS/07-agentic-ai-subsystem-requirements.md#721-orchestrator-agent-nodes-and-when-a-node-may-call-a-model), ADR-010), is a single in-process **Agent Orchestrator** (`AgentWorkflowService`) running all four `IAgentNode`s inside the one API deployable, with model access only through a provider-agnostic `IModelClient` and only from the one node whose input is genuinely free text (Planner) — no separate Python runtime in the target shape. Node 4, Policy Compliance, already matches this target exactly — tool endpoints, a deterministic recommendation step, the rule engine, and the human-approval workflow, no model call anywhere, since its verdict gates a high-impact action (team decision made 2026-09-12). Node 1, Planner, is fully built and wired but not yet in the target shape — a standalone Python/FastAPI/LangGraph service (`planner-agent/`), called over HTTP (`PlannerAgentClient`) from `CreateWorkflowAsync`, which does persist the resulting plan; migrating it to an in-process node calling `IModelClient` is the open item. Node 3, Budget Analysis, is fully built as a standalone Python/LangGraph service (`agent-service/`) with its tool endpoints and a model call used mainly to phrase ranked-option rationale over otherwise-deterministic arithmetic, but isn't wired into the Orchestrator at all yet — under the target design it would move in-process with no model call, ranking rationale templated instead of generated. Node 2, Maintenance Analysis, hasn't started; build it directly in the target shape — in-process, no model call, since its output is closed-form statistics with no free-text input to interpret. Flutter mobile app: 2026-09-14 update — development has started and is ongoing (per team status, not yet reflected in this repo — no `mobile/`/`flutter/` directory exists here as of this update; update this line with real evidence once work lands).

## Agentic AI Subsystem — One Agent per Member

The coursework's minimum acceptance rule requires one stateful graph of four distinct agents (§7.2), each with its own input/output contract and a disjoint tool allow-list (§7.3) — not a chatbot, not four copies of the same prompt. [SRS §7.3](SRS/07-agentic-ai-subsystem-requirements.md#73-agent-specifications), [§12](SRS/12-individual-contribution-and-work-allocation.md) and [§18.3–§18.6](SRS/18-team-roster-and-work-allocation.md) already assign exactly one agent to each member — this table just consolidates what's otherwise spread across those three sections and the four component tables above, so status is visible in one place. No redesign was needed: four is both the coursework's required count and the efficient minimum here (no member without an agent, no redundant agent, nothing to merge or split).

As of 2026-09-15 the target architecture is formalised in [SRS §7.2.1](SRS/07-agentic-ai-subsystem-requirements.md#721-orchestrator-agent-nodes-and-when-a-node-may-call-a-model) and [ADR-010](SRS/appendix-d-architecture-decision-record-index.md): a single in-process **Agent Orchestrator** (`AgentWorkflowService`, owned by Hasitha) sequences all four `IAgentNode` implementations inside the one API deployable and owns the control-plane (timeouts, checkpoints, the deterministic gate, the approval interrupt); only Planner calls a model, and only through a provider-agnostic `IModelClient` (Azure OpenAI / OpenAI / Anthropic / on-prem, chosen by config). This supersedes ADR-005's original per-node Python/LangGraph split.
